# Release automation

One command per task, identical locally and in CI:

| Command | What it does |
|---|---|
| `bundle exec fastlane test` | Build and run the full validation suite on every targeted platform |
| `bundle exec fastlane ios beta` | Build, sign, upload to TestFlight |
| `bundle exec fastlane ios release` | Build, sign, upload to App Store Connect (review submission **off** by default) |
| `bundle exec fastlane ios screenshots` | Capture and frame store screenshots |
| `bundle exec fastlane mac release` | Mac App Store build + upload |
| `bundle exec fastlane mac release_developer_id` | Developer ID build, notarize, staple, verify |

### Signing: there is nothing to preserve

This is the most consequential finding, so it is stated plainly rather than buried:

**The project has no signing configured at all.** All three targets set:

```yaml
CODE_SIGN_IDENTITY: "-"
CODE_SIGNING_REQUIRED: "NO"
CODE_SIGNING_ALLOWED: "NO"
```

with `DEVELOPMENT_TEAM: ""` at the project level. `CODE_SIGN_STYLE: Automatic` is present but inert
while signing is switched off. That configuration exists so CI can build and test without
credentials — it is a *CI convenience*, not a release path.

Consequence: **"wrap, don't replace" has nothing to wrap on the signing side.** There is no verified
signing path to protect, so Phase 3 is a greenfield decision rather than a migration. The one thing
that genuinely exists and is worth wrapping is the CI `xcodebuild` matrix, which the `test` lane
mirrors exactly.

### macOS: neither distribution channel is currently viable

`iBase/iBase.entitlements` is an **empty `<dict/>`** — deliberately so, per `docs/08`, as a
CloudKit-ready placeholder. That means:

| Channel | Hard requirement | Present? |
|---|---|---|
| Mac App Store | `com.apple.security.app-sandbox` entitlement | **No** — App Sandbox is not enabled |
| Developer ID + notarization | Hardened Runtime (`ENABLE_HARDENED_RUNTIME = YES`) | **No** — not set anywhere |

Both are small additions, and the app needs no privileged entitlements — it is entirely offline,
with no network, no file access outside its container, and no hardware use. But neither channel
works until its prerequisite is added, so the macOS lanes **assert these preconditions and fail with
an actionable message** rather than producing an artifact that gets rejected or killed at launch.

### Ambiguities and the choice made

1. **Two schemes.** `iBase` builds the app plus both test targets and archives as Release;
   `iBase-UITests` pre-sets `-ShowcaseData` for manual demoing. **Chose `iBase`** as the shippable
   scheme — it is what CI already validates and the only one with an archive configuration.
2. **macOS distribution shape is not recorded anywhere in the repository.** Nothing indicates
   whether iBase ships to the Mac App Store, via Developer ID direct download, or both. `Info.plist`
   sets `LSApplicationCategoryType = public.app-category.utilities`, which both channels use, so it
   is not a signal. **Chose to implement both shapes as separate lanes with separate entitlements
   files**, because the prompt is right that conflating them is the classic macOS failure: signing
   App Store-shaped entitlements with a Developer ID certificate produces a binary the kernel kills
   on launch. Whoever owns the release picks the lane; neither is the default.
3. **Team ID is unknown.** `DEVELOPMENT_TEAM` is empty and no provisioning profile is committed. All
   identifiers and team IDs therefore come from environment variables — see
   [Required secrets](#required-secrets).

## Signing

**Decision: match is recommended for CI, but is not mandatory, and this repository does not migrate
to it now.**

The prompt's own caution applies directly here: match introduces a second repository and a shared
passphrase to manage, and should not be adopted unless CI signing is actually wanted. Two facts from
this machine shaped the call:

| Identity present locally | Can sign |
|---|---|
| `Developer ID Application: … (S8662L649U)` | macOS Developer ID builds — **verified working** |
| `Apple Development: … (U8TS5JBA8Z)` | development builds only |
| *(no Apple Distribution certificate)* | App Store builds cannot be signed on this machine |

So a **local** Developer ID release works today with no match repository at all, while **any** App
Store upload — iOS or Mac — needs a distribution certificate that does not yet exist.

`setup_signing!` therefore does the honest thing rather than picking one and imposing it:

- **`MATCH_GIT_URL` set** → `match(readonly: true)` fetches the identity. Read-only on purpose:
  release lanes consume certificates, they never mint or revoke them.
- **not set, running locally** → falls back to the keychain, with a warning. This is the solo-
  developer case the prompt says match is overkill for.
- **not set, running on CI** → **fails loudly.** A CI runner has no keychain worth falling back to,
  and silently producing an unsigned artifact is exactly the failure this pipeline exists to prevent.

Run `bundle exec fastlane certificates` to populate a machine once `MATCH_GIT_URL` exists.

### What was actually verified

A real Developer ID archive was produced locally, with no Xcode UI involved:

```
Authority=Developer ID Application: Juan Carlos Estevez Rodriguez (S8662L649U)
Authority=Developer ID Certification Authority
Authority=Apple Root CA
TeamIdentifier=S8662L649U
CodeDirectory … flags=0x10000(runtime)          ← Hardened Runtime on
Entitlements: com.apple.security.app-sandbox only ← no App Store-only entitlements
… valid on disk
… satisfies its Designated Requirement
```

That confirms three things at once: the certificate chain is real, Hardened Runtime is applied (so
notarization will not be refused for its absence), and the Developer ID entitlements file is doing
its job — the binary carries the sandbox and nothing the certificate cannot authorise.

## Known gaps

Stated explicitly rather than left implicit.

- **No automated macOS screenshots.** `snapshot` drives XCUITest against *simulators*, and macOS has
  no simulator, so there is no fastlane path to this. `frameit` can frame Mac screenshots captured
  by other means, but capturing them requires scripting `screencapture` against the running app on a
  real machine. Out of scope, per the platform note. The iOS `screenshots` lane covers iPhone and
  iPad only.
- **App Sandbox and Hardened Runtime are not configured**, so the macOS lanes cannot yet produce a
  shippable artifact — see above. The lanes fail loudly with the exact setting to add.
- **Signing has not been exercised end to end.** No Apple Developer credentials are available in
  this environment, so the signing, TestFlight, notarization, and upload lanes are written but have
  **not** been run against Apple. See `BLOCKED.md` for exactly what was and was not verified.
- **Single locale.** The app is not localized, so `Snapfile` lists `en-US` only. Adding locales
  before localizing the app would produce identical English images under different locale folders.
- **No lint or format gate exists** to wire into the `test` lane. If SwiftLint is added later, add it
  to the `test` lane rather than a separate CI step, so local and CI validation stay identical.
